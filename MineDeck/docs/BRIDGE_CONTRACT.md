# MineDeck ↔ MineScape Bridge contract

This document records the **current cross-product wire contract**, not the larger canonical destination.

MineDeck calls the Java Bridge only on its configured loopback URL, whose default is `http://127.0.0.1:8765`. Every request sends `Authorization: Bearer <token>`. The token is generated by Bridge at `config/minescape/bridge.token`; MineDeck reads that local file on demand, prefers an explicitly configured process-environment override when present, never places the value in JSON/state/logs, and fails closed when it is absent or shorter than 32 characters.

## Implemented by both products now

| Java Bridge route | Wire shape | MineDeck behavior |
|---|---|---|
| `GET /v1/health` | `{status, bridgeVersion, minecraftVersion, worldEpoch, onlinePlayers, observedAt, detail}` | Reports Bridge availability/version/epoch. It does **not** infer Minecraft Online from this response and does not call the epoch a manifest hash. |
| `GET /v1/players` | `{players:[{uuid,currentName,online,accessRole,sessionMode,countsTowardFamilyExploration}]}` | Displays Bridge-known players and combines them with the whitelist ledger. |
| `GET /v1/whitelist` | `{entries:[{uuid,displayName,status,changedAt}]}` | Displays durable whitelist intentions and exact `ACTIVE`, `PENDING_NATIVE_SYNC`, or `SUSPENDED` state. |
| `POST /v1/whitelist` | `{"uuid":"…","displayName":null}` → whitelist entry | Records a UUID-only intention. MineDeck explicitly says role assignment and native Minecraft sync were not performed. |
| `DELETE /v1/whitelist/{uuid}` | `{removed,uuid}` | Removes that durable intention. |
| `GET /v1/family-assist` | `{tickets:[{ticketId,playerId,action,reason,status,createdAt}]}` | Shows tickets in Activity. |
| `POST /v1/family-assist` | `{playerId,action,reason}` → ticket | Sends only `SET_EASY`, `SET_NORMAL`, `START_AT_DAWN`, `RESCUE_TO_PUBLIC_SPAWN`, or `MATCHA_HINT`, and reports `PENDING_RELEASE_GATE_ADAPTER`, `APPLIED`, or `REJECTED` exactly. |

The Bridge exposes no arbitrary console endpoint. MineDeck does not synthesize one.

## Explicitly absent from the current Bridge

MineDeck has dashboard/domain shapes for the following canonical features, but its production adapter returns `accepted: false` and **sends no HTTP request** because no corresponding Java route exists:

- authenticated pending-player request timestamps, expiry, and denial;
- access-role mutation and native Minecraft whitelist synchronization;
- character pardon/new-generation transactions and Mortal Hearts read models;
- settlement scanning/ward registration, fog/map, Matcha progress, loot provenance, stewardship, and rewards;
- clean MineScape/MineJammer stop;
- quiesced backup prepare/complete;
- Steward leases;
- MineJammer compare/parcel promotion.

This is intentional fail-closed behavior. Adding any route requires updating the Java implementation, this document, the typed C# adapter, and cross-product tests together.

## MineDeck’s own dashboard API

The browser never calls Bridge directly. It authenticates separately to loopback MineDeck, receives an HTTP-only SameSite cookie plus anti-forgery token, and calls MineDeck’s `/api/*` routes. `BridgeResponse {accepted,message,operationId?}` is MineDeck’s UI result shape; it is not incorrectly assumed to be the Java Bridge response schema.

## Read-model rules

- Minecraft Online remains a successful Java Server List Ping plus pong. A PID or Bridge response is not sufficient.
- A Bridge-known player missing from the whitelist ledger may be displayed as “known but not whitelisted,” with unknown request time/expiry. MineDeck does not call this cryptographically authenticated pending-request evidence.
- Whitelist status is displayed verbatim. `PENDING_NATIVE_SYNC` is not admission.
- Family Assist `PENDING_RELEASE_GATE_ADAPTER` is a recorded request, not an applied game action.
- Missing character/fog/loot/progress data is rendered as unavailable, not zero progress or an empty explored world.
- An ambiguous timeout is never automatically retried for a mutation.
